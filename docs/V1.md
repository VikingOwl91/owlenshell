# Owlenshell v1 Contract

## Purpose

This document defines what must be true for Owlenshell v1 to be considered a complete daily-driver shell.

It is an acceptance contract, not a loose wishlist.

## v1 Product Definition

> **Owlenshell v1 is a complete daily-driver Wayland desktop shell built around atomic, independently hosted UI surfaces.**

The practical acceptance test is:

> **A real existing daily-driver shell can be replaced by Owlenshell without losing the functionality that matters in everyday use.**

## Core Runtime

### Atomic surfaces

Acceptance:

- independent floating/popup shell UI uses native geometry matching visible interaction geometry
- no output-sized invisible interaction surfaces for small widgets
- hidden surfaces do not intercept input

### Live movement

Acceptance:

- movable floating widgets visibly follow pointer movement while dragging
- movement does not wait until drop to update visual position
- drop persists final semantic placement
- cross-output movement preserves widget state

### Persistent placement

Acceptance:

- user placement survives process restart
- persistence uses semantic output/anchor/offset state
- temporary fallback does not overwrite user intent

### Multi-output fallback

Acceptance:

- when a preferred output genuinely disappears, visible affected widgets migrate to a valid fallback
- no widget remains targeted at a dead output

### Return-home

Acceptance:

- when a preferred output returns, widgets using temporary fallback return automatically where appropriate
- persisted preference remains unchanged through fallback

### Reachability

Acceptance:

- topology changes cannot permanently strand a widget outside all usable output regions
- oversized widgets retain a reachable move/edit region
- no valid output causes deferral rather than arbitrary placement

### Scaling

Acceptance:

- scale 1 works
- fractional scaling is production-supported before v1
- geometry, rendering and input remain aligned across scale changes

### Hotplug

Acceptance:

- outputs can appear/disappear while Owlenshell runs
- affected surfaces migrate without shell restart
- rapid topology changes do not corrupt runtime state

## Surface Policies

### Standard placement

Required:

- top
- bottom
- left
- right
- custom

### Standard modes

Required:

- cover
- float

### Custom modes

Acceptance:

- users can define validated mode policies without patching Owlenshell source
- custom modes cannot violate protected runtime/security invariants

## Input

Required:

- configurable move binding
- visible portable move handle or equivalent
- layout/edit mode
- conflict diagnostics where compositor introspection is available

Acceptance:

- normal widget interactions are not stolen by movement logic
- users are never locked out of moving a widget because a modifier binding is unavailable

## Bar

Required:

- top/bottom/left/right placement
- cover and float behavior
- configurable widget composition
- multiple outputs
- reusable public widget primitives

## Default Widgets

v1 must provide sensible built-in implementations for common daily-driver needs.

Required categories:

- workspaces
- clock
- calendar
- active window/title
- tray
- audio output
- microphone
- MPRIS/media
- network
- Bluetooth
- battery/power
- brightness
- basic system metrics
- power/session actions

The exact visual form may evolve.

## Notifications

Required:

- notification daemon integration
- atomic notification surfaces
- stacking without invisible blocking geometry
- actions
- dismissal
- timeout handling
- notification center/history UI

## OSD

Required:

- volume
- microphone
- brightness

OSDs should reuse shared service state rather than polling independently.

## Clipboard

Required:

- clipboard history UI
- search/filter
- activate/copy selected entry
- security/privacy controls appropriate for stored clipboard data

## Launcher

Required:

- applications
- search
- keyboard navigation
- actions
- extensible providers

Owlry may provide backend functionality, but Owlenshell v1 must ship a functional launcher regardless of final repository boundaries.

## Idle and Lock

Required:

- idle detection
- lock invocation
- atomic lock surfaces
- multi-output coverage
- secure input behavior
- authentication integration

## PAM/Auth

Required:

- PAM-backed authentication boundary
- secrets never exposed to Rune
- clear failure/retry behavior
- ordinary shell widget failures cannot bypass lock behavior

## Styling

Required:

- built-in default theme
- coherent Owlenshell design language
- user theme support
- hot reload
- invalid theme rollback

Target frontend:

- CSS/SCSS-like syntax compiled into a restricted StyleIR

Full browser CSS compatibility is not required.

## Configuration

Required:

- sensible defaults
- declarative config
- version-aware configuration format
- user customization without requiring Rune

## Rune Extensions

Required:

- optional scripting runtime
- typed safe state access
- actions
- formatting
- custom lightweight widgets/hooks

Acceptance:

- built-in shell works with Rune disabled
- broken script does not kill unrelated shell components

## IPC / CLI

Required:

- runtime IPC
- inspection
- control
- reload
- widget open/close/toggle
- layout mode
- state dump
- diagnostic commands

Expected CLI name:

```text
owlenshellctl
```

## Diagnostics

Required:

- output inspection
- placement inspection
- surface inspection
- binding diagnostics
- service health
- startup timing

Wayland/runtime decisions must be observable without source-level debugging.

## Performance

v1 should be measured with a realistic daily-driver configuration.

Targets:

- fast first paint
- effectively zero idle CPU outside intentional timers/events
- low memory overhead relative to comparable programmable shells
- minimal unnecessary wakeups
- no heavy subprocess polling loops

Specific hard budgets should be established after representative widgets/services exist.

## Compositor Support

v1 must provide:

- a generic Wayland baseline
- one primary fully accepted compositor target
- at least one secondary smoke-tested compositor target

Compositor adapters may enhance:

- output identity
- global geometry
- work areas
- focused output
- bindings
- workspace/window integration

The shell must not become architecturally dependent on one compositor.

## Session and UWSM Support

v1 must provide native cooperation when operating inside a UWSM-managed session:

- automatic detection of UWSM session environment
- systemd user session lifecycle cooperation on startup and shutdown
- launcher/action process spawning via `uwsm app` when UWSM is active
- zero breakage or degraded capability when running without UWSM (standalone or direct compositor launch)

## Hot Reload

Required where practical for:

- theme
- config
- Rune
- layout

Invalid new state must not destroy the active valid state.

## Persistence

Required persisted user intent:

- widget placement
- selected surface mode where user-chosen
- configurable size where supported
- layout state

Temporary runtime placement must not be persisted as user intent.

## Accessibility

v1 must avoid making critical shell interaction mouse-only.

Required where technically possible:

- keyboard navigation
- visible focus
- non-drag alternatives
- edit handles
- assistive technology compatibility

## Explicit Non-Goals for v1

v1 does not require:

- a Wayland compositor
- a window manager
- a complete desktop environment
- a display manager/greeter
- perfect support for every compositor
- full browser CSS
- forced absorption of Owlry
- arbitrary Rune access to internal unsafe APIs
- an online Widget Registry / Extension Store (long-term ecosystem direction)
- Model Context Protocol (MCP) agent server (long-term ecosystem direction)
- a public project website (long-term project milestone)
- a shell-owned graphical task switcher / workspace overview (long-term shell UX direction)

## Long-Term Direction vs. Immediate v1 Scope

To preserve roadmap discipline and avoid scope creep prior to a daily-driver release:
- **v1 Focus**: Robust Wayland platform ownership, atomic surfaces, live movement (Stage 4), topology fallback/return-home (Stage 5), typed configuration & native Settings GUI (Stage 6/6b), slice hardening (Stage 7), and essential daily-driver widgets.
- **Post-v1 & Ecosystem Direction**:
  - Model Context Protocol (MCP) server for structured agent introspection and control.
  - Machine-readable documentation endpoints (`llms.txt`, published schema mirrors).
  - Central Widget Registry & native Slint Widget Browser.
  - Public Project Website with interactive demos and registry browser.
  - Shell-owned graphical task switcher (Alt+Tab-style) built on a shared typed toplevel/window model rather than compositor-specific UI.
    - Native Slint overlay with keyboard-forward/reverse cycling and activate-on-release behavior.
    - Optional window thumbnails/previews where standardized capture protocols are available, including `ext_foreign_toplevel_image_capture_source_manager_v1`-style window capture.
    - Multi-output-aware filtering and optional application grouping.
    - Compositor-independent shell UX backed by adapters for focus/activation, workspace and window control where generic Wayland protocols are insufficient.
    - Reuse the same toplevel provider/model for task switcher, taskbar, window overview, window picker and future agent-facing APIs.
    - Natural extension: a Super+Tab-style window/workspace overview without turning Owlenshell into a compositor or window manager.

## v1 Exit Criteria

v1 is ready when all of the following are true:

1. The runtime satisfies atomic-surface invariants.
2. Live movement is usable.
3. Multi-output fallback and return-home are reliable.
4. Fractional scaling works.
5. The default shell covers normal daily-driver shell functions.
6. Lock/auth behavior is security-reviewed.
7. Default configuration is useful without scripting.
8. Customization is possible without forking.
9. Diagnostics make runtime decisions inspectable.
10. A real daily-driver shell can be turned off and Owlenshell can replace it for sustained everyday use.
