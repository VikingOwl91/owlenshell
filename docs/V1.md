# Owlenshell v1 Contract

## Purpose

This document defines what must be true for Owlenshell v1 to be considered a complete daily-driver shell.

It is an acceptance contract, not a loose wishlist.

## v1 Product Definition

> **Owlenshell v1 is a complete daily-driver Wayland desktop shell built around atomic, independently hosted UI surfaces.**

The practical acceptance test is:

> **A real existing daily-driver shell can be replaced by Owlenshell without losing the functionality that matters in everyday use.**

## Core Runtime

### Atomic surfaces

Acceptance:

- independent floating/popup shell UI uses native geometry matching visible interaction geometry
- no output-sized invisible interaction surfaces for small widgets
- hidden surfaces do not intercept input

### Live movement

Acceptance:

- movable floating widgets visibly follow pointer movement while dragging
- movement does not wait until drop to update visual position
- drop persists final semantic placement
- cross-output movement preserves widget state

### Persistent placement

Acceptance:

- user placement survives process restart
- persistence uses semantic output/anchor/offset state
- temporary fallback does not overwrite user intent

### Multi-output fallback

Acceptance:

- when a preferred output genuinely disappears, visible affected widgets migrate to a valid fallback
- no widget remains targeted at a dead output

### Return-home

Acceptance:

- when a preferred output returns, widgets using temporary fallback return automatically where appropriate
- persisted preference remains unchanged through fallback

### Reachability

Acceptance:

- topology changes cannot permanently strand a widget outside all usable output regions
- oversized widgets retain a reachable move/edit region
- no valid output causes deferral rather than arbitrary placement

### Scaling

Acceptance:

- scale 1 works
- fractional scaling is production-supported before v1
- geometry, rendering and input remain aligned across scale changes

### Hotplug

Acceptance:

- outputs can appear/disappear while Owlenshell runs
- affected surfaces migrate without shell restart
- rapid topology changes do not corrupt runtime state

## Surface Policies

### Standard placement

Required:

- top
- bottom
- left
- right
- custom

### Standard modes

Required:

- cover
- float

### Custom modes

Acceptance:

- users can define validated mode policies without patching Owlenshell source
- custom modes cannot violate protected runtime/security invariants

## Input

Required:

- configurable move binding
- visible portable move handle or equivalent
- layout/edit mode
- conflict diagnostics where compositor introspection is available

Acceptance:

- normal widget interactions are not stolen by movement logic
- users are never locked out of moving a widget because a modifier binding is unavailable

## Bar

Required:

- top/bottom/left/right placement
- cover and float behavior
- configurable widget composition
- multiple outputs
- reusable public widget primitives

## Default Widgets

v1 must provide sensible built-in implementations for common daily-driver needs.

Required categories:

- workspaces
- clock
- calendar
- active window/title
- tray
- audio output
- microphone
- MPRIS/media
- network
- Bluetooth
- battery/power
- brightness
- basic system metrics
- power/session actions

The exact visual form may evolve.

## Notifications

Required:

- notification daemon integration
- atomic notification surfaces
- stacking without invisible blocking geometry
- actions
- dismissal
- timeout handling
- notification center/history UI

## OSD

Required:

- volume
- microphone
- brightness

OSDs should reuse shared service state rather than polling independently.

## Clipboard

Required:

- clipboard history UI
- search/filter
- activate/copy selected entry
- security/privacy controls appropriate for stored clipboard data

## Launcher

Required:

- applications
- search
- keyboard navigation
- actions
- extensible providers

Owlry may provide backend functionality, but Owlenshell v1 must ship a functional launcher regardless of final repository boundaries.

## Idle and Lock

Required:

- idle detection
- lock invocation
- atomic lock surfaces
- multi-output coverage
- secure input behavior
- authentication integration

## PAM/Auth

Required:

- PAM-backed authentication boundary
- secrets never exposed to Rune
- clear failure/retry behavior
- ordinary shell widget failures cannot bypass lock behavior

## Styling

Required:

- built-in default theme
- coherent Owlenshell design language
- user theme support
- hot reload
- invalid theme rollback

Target frontend:

- CSS/SCSS-like syntax compiled into a restricted StyleIR

Full browser CSS compatibility is not required.

## Configuration

Required:

- sensible defaults
- declarative config
- version-aware configuration format
- user customization without requiring Rune

## Internationalization and Localization

Internationalization is a v1 architecture requirement even if v1 does not ship complete translations for many languages. User-visible strings must not accumulate as hard-coded implementation details that require a later UI-wide retrofit.

Required foundation:

- a structured localization system suitable for UI messages, with Fluent as the preferred initial direction
- stable message identifiers rather than hard-coded user-facing strings in Rust or Slint
- system locale detection plus an explicit user override
- a defined locale fallback chain
- locale-aware numbers, dates and times where applicable
- pluralization and parameterized messages through the localization layer rather than manual string concatenation
- layouts that tolerate translated text expansion rather than assuming English-sized labels
- architecture that does not make left-to-right layout a permanent invariant; RTL support must remain feasible
- first-run language selection early enough that the remainder of onboarding can use the selected locale
- at least two materially different locales exercised before v1 as an implementation/layout reality check

Acceptance:

- switching locale does not require recompiling Owlenshell
- built-in UI text is sourced through the localization layer
- untranslated messages fall back predictably rather than becoming blank or breaking layout
- translators can work primarily on localization resources without editing Rust or Slint source
- locale-specific date/time/number behavior is not implemented through scattered ad-hoc formatting

Long-term widget/extension direction:

- widget manifests may expose localizable names, descriptions and metadata
- third-party widgets should be able to provide localization resources through the same or a compatible model
- Owlenshell supplies the active locale and fallback behavior so every widget does not need to invent an independent i18n subsystem

Translation breadth may scale independently from the v1 architecture requirement. The important v1 constraint is that adding languages later is a content/community task, not a shell-wide refactor.

## Rune Extensions

Required:

- optional scripting runtime
- typed safe state access
- actions
- formatting
- custom lightweight widgets/hooks

Acceptance:

- built-in shell works with Rune disabled
- broken script does not kill unrelated shell components

## IPC / CLI

Required:

- runtime IPC
- inspection
- control
- reload
- widget open/close/toggle
- layout mode
- state dump
- diagnostic commands

Expected CLI name:

```text
owlenshellctl
```

## Diagnostics

Required:

- output inspection
- placement inspection
- surface inspection
- binding diagnostics
- service health
- startup timing

Wayland/runtime decisions must be observable without source-level debugging.

## Performance

v1 should be measured with a realistic daily-driver configuration.

Targets:

- fast first paint
- effectively zero idle CPU outside intentional timers/events
- low memory overhead relative to comparable programmable shells
- minimal unnecessary wakeups
- no heavy subprocess polling loops

Specific hard budgets should be established after representative widgets/services exist.

## Compositor Support

v1 must provide:

- a generic Wayland baseline
- one primary fully accepted compositor target
- at least one secondary smoke-tested compositor target

Compositor adapters may enhance:

- output identity
- global geometry
- work areas
- focused output
- bindings
- workspace/window integration

The shell must not become architecturally dependent on one compositor.

## Session and UWSM Support

v1 must provide native cooperation when operating inside a UWSM-managed session:

- automatic detection of UWSM session environment
- systemd user session lifecycle cooperation on startup and shutdown
- launcher/action process spawning via `uwsm app` when UWSM is active
- zero breakage or degraded capability when running without UWSM (standalone or direct compositor launch)

## Hot Reload

Required where practical for:

- theme
- config
- Rune
- layout

Invalid new state must not destroy the active valid state.

## Persistence

Required persisted user intent:

- widget placement
- selected surface mode where user-chosen
- configurable size where supported
- layout state

Temporary runtime placement must not be persisted as user intent.

## Accessibility

v1 must avoid making critical shell interaction mouse-only.

Required where technically possible:

- keyboard navigation
- visible focus
- non-drag alternatives
- edit handles
- assistive technology compatibility

## Explicit Non-Goals for v1

v1 does not require:

- a Wayland compositor
- a window manager
- a complete desktop environment
- a display manager/greeter
- perfect support for every compositor
- full browser CSS
- forced absorption of Owlry
- arbitrary Rune access to internal unsafe APIs
- an online Widget Registry / Extension Store (long-term ecosystem direction)
- Model Context Protocol (MCP) agent server (long-term ecosystem direction)
- a public project website (long-term project milestone)
- a shell-owned graphical task switcher / workspace overview (long-term shell UX direction)

## Long-Term Direction vs. Immediate v1 Scope

To preserve roadmap discipline and avoid scope creep prior to a daily-driver release:
- **v1 Focus**: Robust Wayland platform ownership, atomic surfaces, live movement (Stage 4), topology fallback/return-home (Stage 5), typed configuration & native Settings GUI (Stage 6/6b), slice hardening (Stage 7), essential daily-driver widgets, and an i18n-ready UI architecture.
- **Post-v1 & Ecosystem Direction**:
  - Model Context Protocol (MCP) server for structured agent introspection and control.
  - Machine-readable documentation endpoints (`llms.txt`, published schema mirrors).
  - Central Widget Registry & native Slint Widget Browser.
    - Third-party widgets declare a typed capability/permission manifest rather than receiving unrestricted host access.
    - Prefer sandboxed out-of-process execution for untrusted third-party widgets, with a policy abstraction that may use Bubblewrap as the initial Linux backend and can later incorporate mechanisms such as Landlock and seccomp without exposing those implementation details to widgets.
    - Sensitive desktop functionality should be brokered through typed Owlenshell capabilities/providers where practical instead of exposing raw host D-Bus, PipeWire, Wayland, filesystem or other privileged interfaces.
    - Registry submissions pass an automated audit pipeline before human review. Auditing should cover manifest validation, static analysis, dependency/supply-chain checks, suspicious/forbidden API use, sandbox-escape indicators, reproducibility/build integrity, and plausibility of requested permissions relative to widget behavior.
    - Automated audit findings feed human review. Reviewer decisions form a labelled historical corpus that can improve future auditor versions, but production audit policy must not self-modify from its own output: new auditor versions are evaluated against historical reviewed cases before deployment.
    - Published widget versions are immutable and bound to the exact reviewed source/build/manifest/permission set. Any changed payload or new release is a new auditable version.
    - Permission expansion on update must be visible to the user and must not be silently granted.
    - Installation presents the registry-reviewed/recommended policy, while the final effective policy remains under local user control. Users can tighten or otherwise adjust permissions during installation and later from Settings; widgets should degrade gracefully when optional capabilities are denied and clearly report when a required capability is unavailable.
    - Support layered local policy: global defaults, optional trust/profile rules, and per-widget overrides, with effective permissions inspectable through Settings and diagnostics.
    - Treat widget lifecycle management as a first-class native Settings experience rather than a website-only workflow: installed widgets, discovery, installation, updates, permissions, configuration, health and removal should be manageable without leaving Owlenshell.
    - Provide version-aware community reputation/voting. Prefer verified-installation signals over anonymous star inflation; preserve per-version quality signals while also exposing an understandable longer-term widget/maintainer trend.
    - Avoid a single popularity score as the dominant discovery mechanism. Support distinct discovery views/signals such as featured, new, recently updated, popular, highly rated and experimental so established widgets do not permanently crowd out new work.
    - Integrate structured widget issue reporting into Owlenshell. Reports should bind to the exact widget version and may include Owlenshell version, compositor/environment information and relevant provider/sandbox state.
    - Diagnostic attachments are explicit opt-in: before submission, users can inspect and redact exactly what Owlenshell proposes to send. Issue reporting must not become implicit telemetry.
    - Keep normal bug reports, compatibility reports, feature requests and permission concerns structured enough to support triage and machine-assisted analysis. Discussions/comments may exist as threaded support conversations rather than an unmoderated global comment wall.
    - Security vulnerability reports use a separate private disclosure path to the appropriate registry/security reviewers and widget maintainer; potentially exploitable details must not be forced into public issues.
    - Surface maintainer replies, issue status and fix availability inside Owlenshell. A user who reported a problem should be able to see a maintainer response, install the fixing release and optionally confirm whether it resolved the report without being required to visit an external tracker.
    - Use aggregated issue, crash, permission and compatibility signals to prioritize re-audits or human review, not as autonomous proof of maliciousness. Examples include sudden post-release crash increases, unusual permission complaints or compatibility regressions concentrated on a specific release/environment.
    - Expose useful trust/maintenance context in the registry, such as review status, reproducibility status, compatibility evidence, recency of review/update and version-aware user feedback, without presenting any single signal as a guarantee of safety.
    - Design the developer workflow around the same capability model: typed SDK/provider APIs, local development/testing, manifest validation and actionable pre-submission audit feedback should make the secure path the easiest path for widget authors.
    - Long-term UX goal: the complete normal widget lifecycle -- discover, install, configure, place, inspect permissions, update, rate, report problems, follow maintainer responses and remove -- should be possible through native Owlenshell UI without requiring users to understand the registry implementation, Git hosting, sandbox backend, D-Bus, PipeWire or compositor-specific plumbing.
  - Public Project Website with interactive demos and registry browser.
  - Shell-owned graphical task switcher (Alt+Tab-style) built on a shared typed toplevel/window model rather than compositor-specific UI.
    - Native Slint overlay with keyboard-forward/reverse cycling and activate-on-release behavior.
    - Optional window thumbnails/previews where standardized capture protocols are available, including `ext_foreign_toplevel_image_capture_source_manager_v1`-style window capture.
    - Multi-output-aware filtering and optional application grouping.
    - Compositor-independent shell UX backed by adapters for focus/activation, workspace and window control where generic Wayland protocols are insufficient.
    - Reuse the same toplevel provider/model for task switcher, taskbar, window overview, window picker and future agent-facing APIs.
    - Natural extension: a Super+Tab-style window/workspace overview without turning Owlenshell into a compositor or window manager.

## v1 Exit Criteria

v1 is ready when all of the following are true:

1. The runtime satisfies atomic-surface invariants.
2. Live movement is usable.
3. Multi-output fallback and return-home are reliable.
4. Fractional scaling works.
5. The default shell covers normal daily-driver shell functions.
6. Lock/auth behavior is security-reviewed.
7. Default configuration is useful without scripting.
8. Customization is possible without forking.
9. Diagnostics make runtime decisions inspectable.
10. The built-in UI uses the localization foundation and has been exercised with at least two materially different locales.
11. A real daily-driver shell can be turned off and Owlenshell can replace it for sustained everyday use.
