## Definitions and decision record

**Gate R — Research Benchmark:** an evidence-backed eligibility decision for one exact set of candidates, binary/source/fixture/harness revisions, environment, declared workload and measured metric. It permits only the named comparative experiment after separate explicit approval. It is neither a general framework certification nor evidence of production readiness. An R record must identify every excluded behavior and the impact on interpretation; only equally scoped observations may be compared. A candidate missing any mandatory requirement for that specific run is **NO-GO for that run**, not automatically a rejected production renderer.

**Gate P — Production Acceptance:** the complete functional, reliability, integration and operational evidence needed before proposing a renderer selection or requesting a production change. P evaluates the full supported OwlenShell behavior, not just a benchmark fixture. P does not itself authorize selection, code integration or deployment; each requires the maintainer's explicit decision.

Use statuses PASS, FAIL, PARTIAL, UNVERIFIED, BLOCKED and NOT APPLICABLE. Each PASS needs a reproducible evidence reference tied to the tested source tree/commit, exact binary and dependencies, fixture, harness/configuration, environment and test run. NOT APPLICABLE requires an explicit rationale and cannot hide a required behavior. Keep failures, partial observations, exclusions, review findings and subsequent fixes; never rewrite earlier results as if they had passed. A decision record must specify scope, candidate and workload set, metric definitions, run IDs, reviewer and date, each requirement/evidence link, unresolved limitations and maintainer decision. Changing a candidate, workload, compositor/driver or measured condition invalidates the affected approval until reviewed again.

## Gate R: mandatory common requirements

1. **Scope and reproducibility.** Record source revision and clean/dirty state with diff, hashes of tested executables, dependency locks and external libraries, compiler/build profile, harness/configuration and shared fixture, environment including compositor, output geometry/refresh/scale, CPU/GPU/driver/adapter and cache policy. Confirm the same declared workload and comparator conditions. An unavailable metric is recorded as unavailable, not zero.
2. **Isolated setup and cleanup.** Run only in an owned private compositor and explicitly identified socket, without production services or names. Confirm compositor identity and output configuration, bound startup/termination, capture errors and verify tracked owned clients and process groups are gone. Abort affected trials on surviving live processes or uncertain cleanup. The harness is not a containment boundary for untrusted executables.
3. **Surface and scene.** Establish which client connection and native surface carry the measured layer role; associate actual configure/acknowledge and buffer submissions without joining ambiguous numeric IDs across connections. Verify expected policy and geometry on the declared output. Validate the same visible scene and workload content: panel/card dimensions and placement, semantic theme values, representative opaque/transparent/partially transparent areas, clipping and text/icon requirements relevant to that run, using documented tolerances and independent visual inspection where necessary. Screenshot existence, a lone sampled pixel, an unscoped buffer attach or a frame callback is not enough.
4. **Actual workload.** Instrument or observe the state sequence and frame behavior for the named mode and duration; confirm intended 1/2/3-second updates or animation behavior actually reach the visible scene. Verify that candidate workloads have equivalent update rates and visual complexity, with unavoidable differences declared. Timer settings alone do not establish presented cadence. A static-idle run must demonstrate that intended state and animation remain static, but an unexpectedly busy renderer is not excluded for being busy: its redraw/wakeup behavior is a result to measure.
5. **Measurement validity.** Identify what each instrument measures and its attribution, boundaries, sample period and uncertainty. First buffer submission is a startup proxy, not first presentation. Compositor presentation feedback is not physical display latency. Input-to-photon requires suitable external instrumentation. System-wide GPU counters include other processes; GPU utilization is not energy. Capture all trials including failures, randomized or paired order, warm-up/cache/shader conditions, sample counts and spread; do not replace unavailable counters with estimates.
6. **Independent review and approval.** A reviewer must challenge equivalence, association, capture, safety and cleanup, and confirm each claim against raw evidence. The maintainer must explicitly authorize the specific R scope before any comparative run. The existing benchmark guard must not be weakened or bypassed merely because this protocol is approved.

R has **no performance pass threshold**: low CPU, low memory, few wakeups, high FPS or fast startup are outcomes, not entry conditions. Eligibility requires measuring and attributing the requested behavior reliably, not preselecting a winner. Unavailable required evidence blocks that measurement; avoid silently substituting a less demanding metric or scenario.

## Gate R: additional requirements by workload or metric

| Proposed comparison | Additional mandatory evidence | Scope boundary |
|---|---|---|
| Cold/warm startup | Distinguish process start, connection, configure, submission and, where supported, presentation. Record process and shader cache state and binary/profile; retain failed starts. | Do not label a log observation or frame callback as visible first paint. If presentation feedback is absent, report only the identified proxy. |
| Static idle, CPU/RSS/PSS/wakeups/GPU | Prove correct static scene over the full sample; record repaint/submission/event counters and tool attribution, sample lengths and instrumentation overhead. Record total/shared memory separately where available. | Context switches are not wakeups; GPU utilization/memory unavailable or system-wide must be labeled. |
| Periodic updates/theme changes | Verify actual independently scheduled state transitions and resulting visible changes, module values and measured cadence; confirm the same semantic tokens and content. | A clock tick alone does not represent workspace/system updates or a complete theme engine. |
| Animation/frame pacing | Demonstrate the same animation, visual complexity, target schedule and comparable observed frames; use real presentation feedback for presented-frame pacing. | The current blinking text is not automatically equivalent to a spatial animation; unpresented frames are not FPS evidence. |
| Input/latency | Demonstrate an authenticated target surface, deterministic injection phases, coordinates and mapped hit rectangle, delivered pointer/keyboard/scroll event, framework response, and resulting state. Include no-injection/wrong-target controls. | No input-to-photon without external instrumentation. Logging suppression and input translation must be resolved before a marker can serve as the sole result. |
| Scale-specific workload | Validate logical dimensions, buffer dimensions, buffer scale/viewport and output mapping, screenshot geometry/alpha and readable text at the **selected** scale. For input measurements prove logical-to-physical mapping and hit regions there. | Integer-buffer upscaling/downsampling is not native fractional-scale support; a result at one scale does not establish other scales. |
| Multi-panel/output | Verify three independently configured panel instances, output assignment, state, input routing, and isolated surface/lifecycle changes for the scenario being measured. | Separate processes or three overlapping copies do not prove same-process panel independence. Omit the scenario from R only if it is not being measured, explicitly stating the limitation. |
| Shutdown/recreation/output loss | Observe surface destruction, graceful close, process/resource cleanup and, for recreation, state retention and correct new surface/output association; include bounded forced termination separately. | Nested winit off/on is synthetic deactivation, not physical connector removal/reconnection. No physical-hotplug inference. |

For a narrow static single-output R run, multi-panel behavior and real physical hotplug can be declared out of scope rather than falsely passed. They remain mandatory for P and for any R comparison that claims to measure them. Likewise, input may be out of scope for a passive static measurement, but must be resolved for any interaction or input-latency comparison. The gate must be applied to the complete candidate set and requested metrics: do not change the candidate set after seeing unfavorable measurements without recording and reviewing the change.

## Gate P: production acceptance

P retains **all E1–E11** and the A–G acceptance categories from the existing evaluation, with evidence tied to the integration candidate and actual supported hardware/compositors. The production requirements are not reduced by a future narrow R approval:

- **E1 startup/shutdown:** initial and repeated launches, graceful close, forced termination, surface destruction and verified cleanup.
- **E2 static idle:** correct stable panel and observable redraw/wakeup behavior without state changes.
- **E3 periodic updates:** clock, workspace and system updates at independent frequencies with correct state propagation and no accidental cross-module effects.
- **E4 animation:** equivalent deterministic behavior, observable pacing and appropriate handling of missed/coalesced frames.
- **E5 interaction:** pointer, clicks, scroll, keyboard interactivity/focus and restoration, hit testing, input regions and routing between panels.
- **E6 transparency:** transparent, partially transparent and opaque regions, alpha blending/edges, clipping, semantic colors, text and icons, including declared color assumptions.
- **E7 scaling:** 1.00, 1.25, 1.50, 1.75 and 2.00 plus transitions, logical/physical geometry, correct buffers/viewports and input coordinates, readable rendering and mixed scales where supported.
- **E8 output lifecycle:** discovery, loss/addition/reconnection, reassignment, state-preserving surface recreation and cleanup. Label synthetic nested tests separately from supported physical connector tests.
- **E9 multiple panels:** three independently configured panels, distinct arrangements/output assignment and independent same-process state/lifecycle behavior.
- **E10 layer shell:** supported layers, anchors, margins, zones, output selection, keyboard policies, resizing, configure/ack and input regions; verify compositor behavior rather than only requests.
- **E11 stability:** sustained idle/updates, repeated initialization/teardown, recovery, resource growth and no orphaned owned processes.

P additionally requires a reviewed integration plan preserving the shell-owned SCTK platform, domain/output/placement/persistence/coordinator state wherever practical; explicit native-surface and GPU-resource lifetime rules; security, accessibility, packaging, dependency licensing/maintenance review; regression tests of the existing Slint behavior; and end-to-end verification of supported session/compositor combinations. Physical connector or system-integration claims require appropriate real-system evidence, not a nested simulation. P may be BLOCKED when safe isolation or a required physical test is unavailable; do not mark it PASS by assuming nested behavior generalizes.
